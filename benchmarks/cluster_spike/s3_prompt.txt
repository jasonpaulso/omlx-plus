You are reviewing the design of a distributed inference server that shards a single large language model across two machines connected by a high-bandwidth link. Read the following description carefully and then answer the question at the end.

The server accepts HTTP requests on a designated head node. The head node owns the scheduler, which maintains a waiting queue and a running batch. Requests enter the waiting queue on arrival. On each scheduling step, the scheduler admits as many waiting requests into the running batch as the memory budget and the maximum sequence count allow, then performs one batched decode forward pass over every sequence currently in the batch. Sequences that emit an end-of-sequence token, or that reach their token limit, or that are aborted by a disconnecting client, are removed from the batch at the next step boundary, and their key-value cache blocks are released back to the pool.

Tensor parallelism splits each weight matrix across the two machines. Every attention projection and every feed-forward projection is partitioned so that each machine holds one half of the parameters and computes one half of the output. Because the halves must be recombined before the next layer can proceed, each machine performs a collective reduction with the other at every partition boundary. The reduction is a blocking operation: neither machine can continue until both have contributed. This means the two machines execute in lockstep, one forward pass at a time, and any divergence in the sequence of operations they perform will cause the collective to mismatch and the entire system to stall indefinitely.

To keep the machines in lockstep without duplicating scheduling logic, the design elects one machine as the leader. The leader runs the real scheduler. Every time the leader invokes the model, it first broadcasts a small message describing that invocation: which cache slots participate, which token identifiers are being fed in, and which cache slots should be released afterward. The follower machine does not schedule anything at all. It listens for these messages and replays each described invocation against its own half of the weights. Because the follower's work is derived entirely from the leader's broadcast, the two machines cannot diverge, even when the leader makes adaptive local decisions such as choosing a prompt chunk size based on currently available memory.

The cost of this scheme is a coordination tax: the wall-clock time spent broadcasting and waiting that would not be spent if the model ran on one machine. The tax is measured per scheduling step rather than per token, which matters because a single broadcast serves the entire batch. As the batch grows, the same fixed broadcast cost is amortized across more tokens, so the per-token tax falls. A budget is set as a fixed fraction of the measured single-token latency, and the design is rejected if the measured tax exceeds it.

There is a subtlety in how throughput must be measured to tell continuous batching apart from a system that has silently degraded into processing one request at a time. If throughput is computed by summing the individual decode rates of several concurrent requests, a system that runs them strictly one after another scores well, because each request in isolation decodes at full speed and the idle waiting time never appears in any denominator. The measurement must instead divide the total tokens produced by the wall-clock span from the first token that arrives anywhere in the system to the last token that arrives anywhere in the system, so that the gaps introduced by serialization fall inside the window and drag the number down.

Question: in two or three sentences, explain why the follower machine must not run its own scheduler, even though it has enough information to do so.
